# 네이버 요청시 일어나는 일
브라우저에 `www.naver.com`을 입력하면 일어나는 일 <br>

---

## 학습 목표

1. URL 입력부터 화면 렌더링까지의 **전 과정 흐름**을 이해한다.
2. 각 단계(DNS, TCP, TLS, HTTP, 렌더링)에서 일어나는 일을 설명할 수 있다.
3. 네트워크/렌더링 단계에서 발생할 수 있는 **실무 문제와 해결책**을 학습한다.

---

## 전체 흐름 한눈에 보기

```
[1] 사용자 입력: www.naver.com
        ↓
[2] URL 파싱
        ↓
[3] 브라우저 캐시 / HSTS 확인
        ↓
[4] DNS 조회 (도메인 → IP)
        ↓
[5] TCP 3-Way Handshake (연결 수립)
        ↓
[6] TLS Handshake (HTTPS 암호화)
        ↓
[7] HTTP 요청 (GET /)
        ↓
[8] 서버 처리 + HTTP 응답 (HTML)
        ↓
[9] 브라우저 렌더링 (DOM → CSSOM → Render Tree → Paint)
        ↓
[10] 추가 리소스 로딩 (CSS, JS, 이미지, API)
        ↓
[11] JavaScript 실행 + 이벤트 바인딩
        ↓
[12] 사용자에게 페이지 노출 완료
```

이 12단계를 차근차근 뜯어본다.

---

## 1단계: 사용자 입력 (`www.naver.com`)

사용자가 주소창에 `www.naver.com`을 입력하고 Enter를 누른다. 이때 브라우저는 입력된 문자열이 <br>
**URL인지, 검색어인지** 먼저 판단한다. <br>

- `www.naver.com` → 도메인 형식 → URL로 처리
- `naver 주식` → 도메인 형식 X → 기본 검색엔진(Google 등)으로 전송

> 실무 팁: 사용자가 단순히 `naver.com`만 입력해도 브라우저는 자동으로 `https://`를 붙인다.

---

## 2단계: URL 파싱

브라우저는 URL을 구성 요소로 분해한다.

```
https://www.naver.com:443/main?query=hello#section1
└─┬─┘   └────┬─────┘ └┬┘ └─┬┘ └────┬────┘ └───┬───┘
Scheme  Host       Port Path  Query        Fragment
```

| 구성 요소 | 예시 | 설명 |
|---------|-----|------|
| Scheme | `https` | 프로토콜 (http, https, ftp 등) |
| Host | `www.naver.com` | 서버 도메인 |
| Port | `443` | 포트 (HTTPS 기본값 443, HTTP 80) |
| Path | `/main` | 서버 내 리소스 경로 |
| Query | `?query=hello` | 쿼리 파라미터 |
| Fragment | `#section1` | 페이지 내 앵커 (서버 전송 X) |

> 실무 팁: `Fragment`(#)는 **서버로 전송되지 않는다**. 
> 따라서 React Router에서 해시 라우팅(`HashRouter`)을 쓰면 서버에 추가 설정 없이도
> SPA 라우팅이 가능하다.

---

## 3단계: 브라우저 캐시 / HSTS 확인

브라우저는 네트워크 요청을 보내기 전에 캐시를 우선 확인한다.<br>

### 3.1 캐시 확인 순서

```
1. Memory Cache  (메모리, 가장 빠름, 탭 닫으면 사라짐)
2. Disk Cache    (디스크, 영구적)
3. Service Worker Cache (PWA에서 사용)
4. HTTP Cache    (Cache-Control 헤더 기준)
```

캐시 HIT이면 네트워크 요청을 건너뛴다 → 페이지 즉시 로드.

### 3.2 HSTS (HTTP Strict Transport Security)

브라우저는 해당 도메인이 HSTS 목록에 있으면 **무조건 HTTPS로 변환**한다. <br>
`naver.com`은 HSTS preload 목록에 등록되어 있으므로 `http://`로 입력해도 자동으로 <br>
`https://`로 바뀐다. <br>

---

## 4단계: DNS 조회 (도메인 → IP 변환)

`www.naver.com`은 사람이 읽기 위한 이름일 뿐, 실제 통신은 IP 주소 <br>
(예: `223.130.200.107`)로 이루어진다. <br>

### 4.1 DNS 조회 순서

```
[1] 브라우저 DNS 캐시 확인
        ↓ (없으면)
[2] OS 호스트 파일 확인 (/etc/hosts, C:\Windows\System32\drivers\etc\hosts)
        ↓ (없으면)
[3] 라우터 DNS 캐시 확인
        ↓ (없으면)
[4] ISP DNS 서버 (예: KT 168.126.63.1) → 재귀 질의
        ↓
[5] Root DNS → TLD DNS (.com) → Authoritative DNS (naver.com)
        ↓
[6] IP 주소 응답 (예: 223.130.200.107)
```

### 4.2 직접 확인 명령

```bash
# 윈도우/맥/리눅스 공통
nslookup www.naver.com

# 결과 예시
# Name:    www.naver.com.nheos.com
# Address: 223.130.200.219
# Address: 223.130.200.236
```

## 5단계: TCP 3-Way Handshake (연결 수립)

브라우저는 IP를 알아냈으니 이제 서버와 **연결**을 맺어야 한다. 
TCP는 연결 지향 프로토콜이므로 3단계 악수(Handshake)가 필요하다.

```
Client                          Server
  │                                │
  │ ──── SYN (연결 요청) ────────→ │
  │                                │
  │ ←── SYN-ACK (응답 + 동의) ──── │
  │                                │
  │ ──── ACK (확인) ─────────────→ │
  │                                │
  │       (연결 완료)               │
```

| 단계 | 의미 |
|------|-----|
| SYN | "연결할까요?" (Synchronize) |
| SYN-ACK | "네, 그럼 저도 연결합시다" |
| ACK | "확인했습니다, 시작합니다" |

"서로 통신이 가능한지 확인하고 연결을 수립하는 3단계 절차" 이것을 Handshake 라고 함.

---

## 6단계: TLS Handshake (HTTPS 암호화 협상)

`https://www.naver.com`이므로 TCP 연결 위에 **TLS 암호화 채널**을 추가로 만든다.

```
Client                                      Server
  │                                            │
  │ ── ClientHello (지원 암호화 목록) ───────→ │
  │                                            │
  │ ←── ServerHello + 인증서 + 공개키 ──────── │
  │                                            │
  │ (인증서 검증: CA 체인 확인)                 │
  │                                            │
  │ ── 세션키(대칭키) 암호화 전송 ──────────→ │
  │                                            │
  │ ←── Finished ────────────────────────────── │
  │                                            │
  │       (이후 모든 통신은 대칭키로 암호화)   │
```

### 핵심 포인트

- **비대칭 암호화**(공개키/개인키)는 초기 세션키 교환에만 사용
- **대칭 암호화**(AES 등)는 실제 데이터 전송에 사용 (빠르기 때문)
- 인증서는 CA(Certificate Authority)가 서명한 것으로, 위변조 불가

## 7단계: HTTP 요청 전송

연결이 완성되었으면 이제 실제 데이터를 요청한다. 브라우저는 다음과 같은 **HTTP Request 메시지**<br>
를 전송한다. <br>

```http
GET / HTTP/2
Host: www.naver.com
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 ...
Accept: text/html,application/xhtml+xml,application/xml;q=0.9,*/*;q=0.8
Accept-Language: ko-KR,ko;q=0.9,en-US;q=0.8,en;q=0.7
Accept-Encoding: gzip, deflate, br
Cookie: NID_AUT=xxx; NID_SES=yyy
Connection: keep-alive
```

### 주요 헤더 의미

| 헤더 | 역할 |
|-----|-----|
| `Host` | 가상 호스팅 시 어느 도메인용 요청인지 식별 |
| `User-Agent` | 브라우저/OS 정보 (서버에서 모바일/PC 구분에 사용) |
| `Accept` | 받을 수 있는 컨텐츠 타입 |
| `Accept-Encoding` | 압축 방식 (gzip, br/Brotli) |
| `Cookie` | 인증/세션 정보 자동 전송 |

## 8단계: 서버 처리 + HTTP 응답

naver의 서버(실제로는 로드밸런서 → 여러 WAS)가 요청을 받아 처리한 후 응답을 보낸다.<br>

### 8.1 일반적인 서버 처리 흐름 (naver 추정)

```
[Client]
    ↓
[CDN (Akamai/자체 CDN)]  ← 정적 리소스 캐시
    ↓
[L4/L7 Load Balancer]
    ↓
[Web Server (Nginx/Apache)]
    ↓
[WAS (Java/자체 서버)]
    ↓
[Cache (Redis/Memcached)]
    ↓
[DB (MySQL/Oracle)]

# Memcached는 Memory Cache Daemon에서 유래
# 메모리(RAM)에 데이터를 저장해 두었다가 매우 빠르게 꺼내 쓰기 위한 분산 캐시 서버임.
```

### 8.2 HTTP Response 예시

```http
HTTP/2 200 OK
Content-Type: text/html; charset=UTF-8
Content-Encoding: br
Cache-Control: no-cache, no-store, must-revalidate
Set-Cookie: NID_AUT=xxx; Path=/; Domain=.naver.com; HttpOnly; Secure
Server: nginx
Content-Length: 89432

<!DOCTYPE html>
<html lang="ko">
<head>
  <meta charset="UTF-8">
  <title>NAVER</title>
  ...
</head>
<body>
  ...
</body>
</html>
```

### 8.3 응답 상태 코드

| 코드 | 의미 | 실무 예 |
|------|-----|--------|
| 200 | 성공 | 정상 페이지 로드 |
| 301/302 | 리다이렉트 | `http://` → `https://` 전환 |
| 304 | Not Modified | 캐시 사용 가능 |
| 401 | 인증 필요 | 로그인 토큰 만료 |
| 403 | 권한 없음 | 접근 차단 |
| 404 | 없음 | 잘못된 URL |
| 500 | 서버 오류 | 백엔드 버그 |
| 502 | Bad Gateway | WAS 다운, 로드밸런서가 502 반환 |
| 503 | Service Unavailable | 서버 과부하 |

## 9단계: 브라우저 렌더링 (Critical Rendering Path)

서버에서 HTML을 받아왔으니 이제 화면에 그려야 한다.

```
[1] HTML 수신 (스트리밍 방식, 한꺼번에 X)
        ↓
[2] HTML 파싱 → DOM Tree 생성
        ↓
[3] <link rel="stylesheet"> 만나면 CSS 다운로드 시작 (병렬)
        ↓
[4] CSS 파싱 → CSSOM Tree 생성
        ↓
[5] DOM + CSSOM → Render Tree 생성
        ↓
[6] Layout (Reflow): 위치/크기 계산
        ↓
[7] Paint: 픽셀 그리기
        ↓
[8] Composite: 레이어 합성 → 최종 화면
```

### 9.1 `<script>` 만나면 어떻게 될까?

- 일반 `<script>`: HTML 파싱 **중단** → 스크립트 다운로드/실행 → 파싱 재개
- `<script async>`: 다운로드 병렬, 실행은 즉시 (HTML 파싱 중단됨, 짧게)
- `<script defer>`: 다운로드 병렬, 실행은 HTML 파싱 완료 후

## 12단계: 사용자에게 페이지 노출 완료

브라우저는 다음 4가지 핵심 성능 지표를 측정한다 (Web Vitals).

| 지표 | 의미 | 권장값 |
|------|-----|-------|
| **FCP** (First Contentful Paint) | 첫 콘텐츠가 그려진 시점 | < 1.8s |
| **LCP** (Largest Contentful Paint) | 가장 큰 콘텐츠 표시 시점 | < 2.5s |
| **TBT** (Total Blocking Time) | JS 블로킹 누적 시간 | < 200ms |
| **CLS** (Cumulative Layout Shift) | 레이아웃 변동 누적 | < 0.1 |

> 실무 팁: Chrome DevTools → Lighthouse 탭에서 측정 가능. 
> naver.com을 Lighthouse로 측정해보면 어떤 최적화 기법을 쓰고 있는지 한눈에 보인다.

### 실습 4) 직접 HTTP 요청 보내기 (Node.js)

```javascript
// http-test.js
// 풀스택 환경에서 백엔드(NestJS/Spring) → 외부 API 호출 시 사용하는 방식

import https from 'https';

const options = {
  hostname: 'www.naver.com',
  port: 443,
  path: '/',
  method: 'GET',
  headers: {
    'User-Agent': 'Mozilla/5.0 (test-client)',
  },
};

// HTTPS 요청 생성
const req = https.request(options, (res) => {
  // 응답 헤더 출력
  console.log('상태 코드:', res.statusCode);
  console.log('응답 헤더:', res.headers);

  // 응답 본문 수신
  let body = '';
  res.on('data', (chunk) => {
    body += chunk;
  });
  res.on('end', () => {
    console.log('본문 길이:', body.length, 'bytes');
    console.log('본문 일부:', body.slice(0, 200));
  });
});

// 에러 처리 (실무 필수)
req.on('error', (error) => {
  console.error('요청 실패:', error.message);
});

req.end();
```

**실행 방법**

```bash
node http-test.js
```

## 핵심 개념 체크리스트

- [ ] URL 입력 시 브라우저는 URL인지 검색어인지 먼저 판단한다.
- [ ] URL은 Scheme, Host, Port, Path, Query, Fragment로 구성된다.
- [ ] 브라우저는 네트워크 요청 전에 캐시를 먼저 확인한다.
- [ ] HSTS가 적용된 사이트는 HTTP로 입력해도 HTTPS로 자동 전환된다.
- [ ] DNS의 역할은 도메인 이름을 IP 주소로 변환하는 것이다.
- [ ] HTTP 응답을 받으면 브라우저는 DOM → CSSOM → Render Tree → Paint 순으로 렌더링한다.
- [ ] DNS 조회는 브라우저 → OS → 라우터 → ISP DNS → 권한 DNS 순으로 진행된다.
- [ ] TCP 연결은 3-Way Handshake를 통해 수립된다.
- [ ] 브라우저는 HTTP Request 메시지를 서버로 전송한다.
- [ ] HTTP Request에는 Host, User-Agent, Cookie 등의 헤더가 포함될 수 있다.
- [ ] 서버는 요청을 처리한 후 HTTP Response를 반환한다.
- [ ] 브라우저는 HTML을 파싱하여 DOM Tree를 생성한다.
- [ ] 브라우저는 CSS를 파싱하여 CSSOM Tree를 생성한다.
- [ ] 브라우저에 www.naver.com을 입력하면 캐시 → DNS → TCP → TLS → HTTP → 렌더링 순으로 페이지가 표시된다.

## 과제 (선택)

1. `curl -v https://www.naver.com` 결과를 캡처해 **DNS, TCP, TLS, HTTP** 단계가 각각 어디서 일어나는지 표시하라.
2. Chrome DevTools Network 탭에서 `www.naver.com` 첫 진입 시 가장 오래 걸리는 리소스 3개를 찾고, 그 원인을 분석하라.
